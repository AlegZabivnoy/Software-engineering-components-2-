# ADR 0004: Activity діаграма для процесу оформлення замовлення (UC-03)

## Контекст
Завдання 4 вимагає описати процес UC-03 однією формою: Activity діаграмою, BPMN або машиною станів. Процес має показати всі сценарії US-01 і US-02, ролі, розгалуження, паралельні дії та повідомлення в Nova Poshta API з реакцією на відповідь і її відсутність

## Розглянуті альтернативи

**Варіант A — машина станів (stateDiagram-v2) для об'єкта «Замовлення»**
* Плюси: чітко видно статуси замовлення (нове, сплачене, відправлене, доставлене, скасоване)
* Мінуси: відповідає на питання «в яких станах буває замовлення», а не «що зробити і хто»; зникають ролі й повідомлення Новій Пошті; вибір відділення і нестача товару відбуваються ще до появи замовлення

**Варіант B — BPMN**
* Плюси: багата нотація подій і пулів, стандарт для бізнес-процесів
* Мінуси: надлишковий для одного процесу всередині системи; потрібен окремий редактор (bpmn.io), а не текстовий опис поруч із рештою діаграм

**Варіант C — Activity діаграма (Mermaid flowchart)**
* Плюси: показує всі чотири сценарії як шляхи на одній діаграмі; є swimlanes, розгалуження, fork/join і надсилання повідомлення; текстовий опис у Mermaid, як і інші діаграми проєкту
* Мінуси: у Mermaid немає рідних fork/join і фігури прийому події — їх емулюю стилем вузлів

## Рішення
Обрано варіант C: Activity діаграма `Diagrams/activity-uc03.mmd` зі swimlanes Клієнт, Система, Nova Poshta API

## Наслідки
* Кожен Gherkin сценарій UC-03 трасується на окремий шлях (таблиця в `spec.md`)
* Деталі реалізації (виклики методів, транзакція) залишаються на sequence діаграмах, Activity — на рівні процесу
* Статуси замовлення на Activity не моделюються; якщо знадобиться описати життєвий цикл замовлення, це буде окрема машина станів
