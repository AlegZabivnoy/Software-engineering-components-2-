# DEFENSE Завдання 5 - Архітектура (Component Diagram)

## Намір і критерії (1–2 речення)
Описати архітектуру магазину діаграмою компонентів: компоненти, інтерфейси, залежності, межу системи та зовнішні інтеграції
Критерії: кожен компонент і залежність трасуються до даних, вимог, взаємодії або процесу, кожен required інтерфейс має свій provided, зовнішні системи лежать поза межею, учасники sequence діаграм відповідають компонентам

## Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:
**Зовнішні системи намальовані як інтерфейси** У spec Payment API, Nova Poshta API і хмарне сховище - зовнішні системи, а на діаграмі, яку згенерував AI, вони вийшли кружками інтерфейсами, тож межа системи була нечіткою
Виправлення: оголосив їх як `component` зі стереотипом «зовнішня система» поза межею, перерендерив діаграму
Коміт виправлення:https://github.com/AlegZabivnoy/Software-engineering-components-2-/commit/3fea7ec79809ddbeb80747c1b2894c5e1cbafc3f

**Інтерфейси без операцій** Завдання вимагає визначені provided/required інтерфейси, а в spec були лише їхні назви, при цьому ADR 0005 стверджував, що операції описані в spec
Виправлення: додав у spec операції інтерфейсів з джерелом кожної (sequence або вимога), прибрав хибне твердження з ADR 0005
Коміт виправлення: https://github.com/AlegZabivnoy/Software-engineering-components-2-/commit/2780348c9d45f5978b55a89bdd6e5e8f2c6ad8f8

**На sequence діаграмах немає Backend API** На компонентній діаграмі UI звертається до сервісів через Backend API, а на sequence діаграмах WebUI викликав OrderService і DeliveryService напряму, тобто моделі суперечили одна одній
Виправлення: додав критерій «учасники sequence відповідають компонентам архітектури», потім додав учасника Backend API в обидві sequence діаграми й оновив трасування
Коміт виправлення: https://github.com/AlegZabivnoy/Software-engineering-components-2-/commit/261e6322d11abb6503c0b95278aed35359d7bb90

## Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):
Рішення: компонентна діаграма в PlantUML — `adr/0005-component-diagram-plantuml.md`
Альтернативи: Mermaid flowchart (рендериться на GitHub, але немає UML нотації інтерфейсів, компоненти лише імітуються вузлами) і Mermaid C4 (це нотація C4, а не UML, немає provided/required інтерфейсів)
Чому PlantUML: це справжня UML нотація компонентів та інтерфейсів, межу системи видно як прямокутник, і PlantUML уже використаний для use case діаграми. Мінус — GitHub не рендерить `.puml`, тому поруч лежить PNG

## Перевірка — узгодженість із усім ланцюгом моделей (як перевірив):
* Дані → архітектура: кожен репозиторій відповідає групі сутностей ER моделі, база даних зберігає всі сутності
* Вимоги → архітектура: кожен компонент має свої Req або UC, зовнішні системи - свої вимоги (Payment API - Req-02, Nova Poshta API - Req-05, Req-15, Req-16, хмарне сховище - NFR-01)
* Взаємодія → архітектура: учасники sequence діаграм є компонентами, а повідомлення на них - це операції інтерфейсів (`createOrder`, `getBranches`, `saveOrder`, `decreaseStock`)
* Процес → архітектура: компоненти «Система (магазин)» activity діаграми є на компонентній діаграмі
* Як перевірив: пройшов таблиці «Компонент → попередні моделі» і «Залежність → джерело» у `traceability.md` по кожному рядку, перевірив, що кожен required інтерфейс має provided, і перевірив рендери `Diagrams/overview-render.png` та `Diagrams/backend-render.png` на офіційному PlantUML: на обох видно обидва кінці кожної залежності
